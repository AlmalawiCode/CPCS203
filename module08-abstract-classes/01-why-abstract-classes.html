1 Critical Distinction — Abstract Class ≠ Abstraction

🚨 Read This Before Anything Else!

In this module we study abstract classes — a Java keyword and mechanism.
This is NOT the same as the 2nd pillar of OOP called "Abstraction".

Many students confuse these two. Let us be absolutely clear:

❌
Abstraction (2nd OOP Pillar)
  • An OOP design principle
  • Hiding internal details from users
  • Showing only what is necessary
  • Example: you drive a car without knowing its engine internals
  • Achieved by interfaces, encapsulation, abstract classes
✅
Abstract Class (Java Mechanism)
  • A Java language feature (abstract keyword)
  • A class that cannot be instantiated
  • May contain abstract methods (no body)
  • Must be subclassed to be used
  • This module's topic!
💡 One Sentence Summary

Abstraction is the concept (what we want to achieve). Abstract class is one tool in Java that helps us achieve it — but they are not the same thing.

2 What Does "Abstract" Mean?

Before we write a single line of code, we must understand the word itself. Programming is built on real-world thinking, so let us start with the English meaning.

🕐
ABSTRACT idea
Vague • General • Incomplete
Not tied to one specific thing

"Shape" — you picture something,
but which shape exactly?

"Animal" — exists, but which one?
"Vehicle" — but what kind?
📋
CONCRETE idea
Specific • Clear • Complete
Represents one definite thing

"Circle" — no doubt, you know it!

"Cat" — specific, exists in reality
"Car" — clear, identifiable object

← More abstract (cannot be a specific object) More concrete (specific, real object) →
🔑 The Key Insight

In the real world, the definition of an object (from OOP) is: an entity that represents a specific, identifiable thing in the real world. An abstract concept does not satisfy this definition — you cannot point at a "shape" sitting on a table. You can only point at a circle, a rectangle, or a triangle.

3 Class Discussion — Discovering Abstract Classes

Story 1 🖌 The Professor and the Shape

🏫 In the classroom...

👨‍🏫 The Professor says:
My students — please take out a paper and draw a shape.
👤 A student draws a circle and shows it.
(proudly shows a circle)
👨‍🏫 The Professor smiles and says:
I did not say draw a circle. I said draw a shape.
The student pauses...
Yes, a circle IS a shape — absolutely correct! But I said "shape", not "circle". So which shape did I mean? A square? A triangle? You cannot know, because "shape" does not specify a particular object!
👤 Another student:
Okay doctor, what if you asked me to color a shape?
👨‍🏫 The Professor:
Exactly the same problem! You cannot color a "shape" — you can color a circle, or a rectangle. The concept "shape" is too general.

Conclusion: "Shape" does not represent a specific object. It is an abstract concept.

Here you are, professor!
👨‍🏫 The Professor:
Good — but notice what you did. I said "animal" and you brought a specific one — a goat. You had to choose something specific, because you cannot hand a guest just an "animal". You must bring a goat or a sheep.

This is the key: "animal" does not represent a specific object in reality. It is an abstract idea. The concrete things are: goat, sheep — each is specific and identifiable.
🌟 The Insight:
The definition of an OOP object is: an entity with identity that represents a specific, identifiable thing in the real world — no doubt about what it is.

"Animal" fails this test → abstract.
"Goat" passes it → concrete.
"Shape" fails this test → abstract.
"Circle" passes it → concrete.

Therefore: it is not logical to create an object of "Animal" or "Shape".
❓ Slide 3 — Think About It Slide 3

Q1. Do you think it is logical to create an object of class Animal?

No. "Animal" does not describe one specific, identifiable thing — you cannot point at "an animal" that is not also a cat, a dog, a goat… An object must be a specific thing, so creating a plain Animal object makes no sense.

Q2. Do you think it is logical to create an object of class Cat or Dog?

Yes. A cat or a dog is a specific, concrete thing that really exists, so new Cat() and new Dog() are logical. Cat and Dog are concrete classes.

Q3. So why do we need the Animal class?

Because Animal is still useful even if we never create a plain Animal object:

  • Inheritance — it holds what all animals share (e.g. name, eat()) once, instead of repeating it in Cat, Dog, Goat…
  • Polymorphism — one Animal reference, array or parameter can hold any kind of animal (Animal[] farm = { new Cat(), new Dog() };).

It is the same answer as for Shape — see Section 4. In Java we mark such a class abstract (Section 6).

4 "Then Why Have Shape at All?"

If we agree we cannot create an object of Shape — a smart student will raise their hand:

👤 Student asks:
Doctor, if we cannot create an object of Shape, then why do we have it at all? Why not just define Circle, Rectangle, and Triangle directly?
👨‍🏫 The Professor:
Excellent question — I love it! There are two powerful reasons:
♱
Reason 1 — Inheritance

Circle, Rectangle, and Triangle all share common attributes (e.g., color) and common behaviors (e.g., getColor()). Without Shape, we would repeat this code in every subclass. Inheritance eliminates redundancy.

🔄
Reason 2 — Polymorphism

To treat Circle, Rectangle, and Triangle polymorphically (one array, one loop, one method), they must be related by an IS-A relationship. Shape provides that common ancestor. No Shape = no polymorphism between them.

📌 The Answer in One Sentence

We keep Shape because we need it for inheritance (shared attributes/methods) and polymorphism (IS-A relationship) — even though we never create a Shape object directly.

5 The Student Problem — Undergrad, MSc or PhD

📝 The problem Slides 4–5
  • Students are either undergraduate, MSc or PhD.
  • We want to guarantee that nobody creates a Student object. The application always creates a specific kind of Student.

UML: the name of an abstract class is written in italics (or marked {abstract}).

❓ How can we apply the above requirements? Slide 4

Declare Student as an abstract class: public abstract class Student { ... }. The compiler then rejects every new Student(), so the program can only create an Undergrad, an MscStudent or a PhdStudent. We do not rely on programmers "remembering" the rule — the compiler enforces it.

❓ Why do we have the Student class in the first place? Slide 5

If nobody may create a Student object, why not just write the three subclasses?

  1. A common implementation of common aspects of all students — e.g. setLogin() and getLogin() are written once in Student and inherited by all three subclasses.
  2. A place holder in the hierarchy that corresponds to a significant concept in the problem domain — "student" is a real idea in a university system even though every real student is one specific kind.
  3. To handle all students independently of their subclass, using the type Student and polymorphism — e.g. one Student[] array, or a method void printLogin(Student s) that works for every kind of student.
🔑 Same pattern as Animal and Shape

Animal, Shape and Student are all general concepts: never instantiated, but kept for shared code (inheritance) and a common type (polymorphism). The full Student code is in Lesson 2, Section 2.

6 Abstract Classes — The Definition

In an inheritance hierarchy, superclasses become more general and subclasses become more specific. Going up the tree (Camel → Mammal → Animal), a class can become so general that it no longer describes any real object. Such a class should be abstract.

📌 Definition — Abstract Class Slide 6
  • You must declare the class with the keyword abstract: abstract class MyClass { ... }
  • An abstract class cannot be instantiated using the new operator.
📄 Declaring an abstract class ▼
abstract class MyClass { // the keyword abstract goes before class // fields, constructors and methods as usual } abstract class Student { } // our Student from slides 4-5 // Student s = new Student(); // compile error: // "Student is abstract; cannot be instantiated"
❓ Quick check

In the hierarchy Animal → Mammal → Camel, which classes would you declare abstract, and what happens to new Mammal()?

Animal and Mammal are general (no real animal is "just a mammal"), so both should be abstract. Camel is specific, so it stays concrete. new Mammal() then gives the compile error "Mammal is abstract; cannot be instantiated", while new Camel() is fine. What goes inside an abstract class (fields, constructors, abstract methods) is the subject of Lesson 2 and Lesson 3.
