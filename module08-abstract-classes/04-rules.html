📜 The Rules of Abstract Classes

What is legal, what is not, and why

1 The Rules of Abstract Classes

Study each rule carefully. Each one has an example to make it concrete.

1 Subclass implements ALL abstract methods → it becomes concrete and can be instantiated

If a subclass provides a @Override implementation for every abstract method it inherited, the compiler considers it complete — it becomes a normal (concrete) class and you can create objects of it.

👁︎ Show Example▼
abstract class Shape { public abstract double getArea(); public abstract double getPerimeter(); } class Circle extends Shape { private double radius; public Circle(double r) { radius = r; } @Override public double getArea() { return Math.PI * radius * radius; } // ✓ implemented @Override public double getPerimeter() { return 2 * Math.PI * radius; } // ✓ implemented } // → Circle is concrete: new Circle(5) is VALID ✓
2 Subclass does NOT implement all abstract methods → it must remain abstract

If a subclass implements some but not all abstract methods, it is still incomplete. The compiler forces it to also be declared abstract.

👁︎ Show Example▼
abstract class Shape { public abstract double getArea(); public abstract double getPerimeter(); } // RegularShape implements getPerimeter (all sides equal) but NOT getArea abstract class RegularShape extends Shape { protected int sides; protected double sideLength; public RegularShape(int sides, double len) { this.sides = sides; sideLength = len; } @Override public double getPerimeter() { return sides * sideLength; } // ✓ implemented // getArea() is still inherited as abstract → must stay abstract! } class RegularHexagon extends RegularShape { public RegularHexagon(double side) { super(6, side); } @Override public double getArea() { return (3 * Math.sqrt(3) / 2) * sideLength * sideLength; } // → Now complete! new RegularHexagon(5) is VALID ✓ }
3 A class that contains any abstract method MUST be declared abstract

You cannot have an abstract method inside a non-abstract class. The class becomes incomplete the moment it contains an abstract method, so it must be abstract too.

👁︎ Show Example▼
// ❌ ILLEGAL — cannot have abstract method in non-abstract class class BadClass { public abstract void doSomething(); // ERROR! } // ✓ CORRECT — abstract method requires abstract class abstract class GoodClass { public abstract void doSomething(); // OK! }
4 If a non-abstract class extends an abstract class, it MUST implement ALL inherited abstract methods

Even if the developer does not plan to use a particular method — they must still implement it. The compiler enforces this with no exceptions. This is exactly what we want!

👁︎ Show Example — The Forgotten Pentagon▼
abstract class Shape { public abstract double getArea(); public abstract double getPerimeter(); } // ❌ COMPILE ERROR — Pentagon forgot to implement getPerimeter()! class Pentagon extends Shape { private double side; public Pentagon(double s) { side = s; } @Override public double getArea() { return 1.72 * side * side; } // getPerimeter() is missing! → Compiler error: "Pentagon is not abstract // and does not override abstract method getPerimeter() in Shape" } // ✓ CORRECT — implements both class Pentagon extends Shape { private double side; public Pentagon(double s) { side = s; } @Override public double getArea() { return 1.72 * side * side; } @Override public double getPerimeter() { return 5 * side; } }
5 An abstract class CAN have zero abstract methods (all methods can be concrete)

You can declare a class abstract even if it has no abstract methods at all. In this case you cannot create instances of the class using the new operator; the class is used as a base class for defining new subclasses Slide 17. This is useful when the class is logically incomplete, even though all its methods have implementations.

👁︎ Show Example▼
// Valid! No abstract methods, but still abstract (cannot be instantiated) abstract class Animal { private String name; public Animal(String name) { this.name = name; } public String getName() { return name; } // concrete public void eat() { System.out.println("eating"); } // concrete // No abstract methods — but still abstract! // Why? Because "Animal" is not a specific enough object. } class Cat extends Animal { public Cat(String name) { super(name); } // No need to override anything — but Cat IS concrete, so new Cat("Tom") is valid }
📌 Why do this?

Sometimes the concept is not logical to instantiate (like Animal or Vehicle), even if all behaviors have reasonable default implementations. Making it abstract expresses this design intent clearly.

6 A subclass CAN be abstract even if its superclass is concrete

Abstractness does not flow only top-down. A subclass of a concrete class can itself be abstract. A famous real-world example: the Object class in Java is concrete — yet Shape (which extends Object) can be abstract.

👁︎ Show Example▼
// Object is concrete (java.lang.Object) // Yet Shape extends Object and is abstract — perfectly legal! abstract class Shape extends Object { // Object is concrete! public abstract double getArea(); } // Similarly: class ConcreteA { // concrete public void hello() { System.out.println("Hello!"); } } abstract class AbstractB extends ConcreteA { // abstract extends concrete! public abstract void work(); // inherits hello() from ConcreteA — still abstract because of work() }
❓ A subclass can be abstract even if its superclass is concrete. Example? Slide 17

The Object class is concrete (new Object() is legal), but its subclasses, such as Shape, may be abstract: abstract class Shape extends Object automatically. Another example from this module: GeometricObject (abstract) extends Object (concrete).

7 An abstract class CAN be used as a data type (polymorphic variable, array, method parameter)

Even though you cannot create a new Shape(), you CAN declare a variable, an array, or a method parameter of type Shape. This is the foundation of polymorphism!

👁︎ Show Example — 3 Forms of Polymorphism▼
// 1. Polymorphic VARIABLE ────────────────────────────────────── Shape s = new Circle("Red", 5); // Shape reference, Circle object → legal! System.out.println(s.getArea()); // dynamic binding → Circle.getArea() // 2. Polymorphic ARRAY ──────────────────────────────────────── Shape[] shapes = new Shape[3]; // array of Shape type → legal! shapes[0] = new Circle("Red", 5); shapes[1] = new Rectangle("Blue", 4, 6); shapes[2] = new Triangle("Green", 3, 4, 5); for (Shape sh : shapes) System.out.printf("Area = %.2f%n", sh.getArea()); // polymorphism! // 3. Polymorphic METHOD PARAMETER ────────────────────────────── public static void printInfo(Shape s) { // accepts any Shape! System.out.println("Area: " + s.getArea()); } // Call it with any concrete Shape: printInfo(new Circle("Red", 7)); printInfo(new Rectangle("Blue", 3, 5));
8 A subclass CAN override a concrete (non-abstract) method and make it abstract

This is a powerful and often surprising rule. A subclass can take a method that was fully implemented in its parent, and re-declare it as abstract — forcing its own subclasses to provide a new implementation. This is the basis of the Manager Technique in Section 5; the slide example is in Section 4.

👁︎ Show Example — Inheriting toString and making it abstract▼
// Object has a concrete toString() method // We can extend Object and redeclare toString() as abstract: abstract class MustPrint extends Object { // Override the CONCRETE toString() from Object → make it ABSTRACT here! @Override public abstract String toString(); // forces all subclasses to implement it } class Student extends MustPrint { private String name; private int age; public Student(String name, int age) { this.name = name; this.age = age; } @Override public String toString() { // COMPILER forces this! return "Student[" + name + ", age=" + age + "]"; } }

2 Are the Following Codes Correct? — Star, Circle and draw()

Version 1 Shape is a normal class Slide 18

📄 Slide 18 — Shape has no draw() ▼
class Shape { ... } class Star extends Shape { void draw() { ... } ... } class Circle extends Shape { void draw() { ... } ... }
❓ Are the following codes correct?
Shape someShape = new Star();
someShape.draw();
  • Shape someShape = new Star(); — legal, because a Star is a Shape.
  • someShape.draw(); — syntax (compile) error, because some Shape might not have a draw() method. The compiler only looks at the declared type Shape, and class Shape has no draw().

Remember: a class knows its superclass, but not its subclasses. Shape does not know that Star and Circle added draw().

📄 Slide18.java — try it yourself ▼
class Shape { } class Star extends Shape { void draw() { System.out.println("Drawing a star"); } } class Circle extends Shape { void draw() { System.out.println("Drawing a circle"); } } public class Slide18 { public static void main(String[] args) { Shape someShape = new Star(); // legal: a Star is a Shape someShape.draw(); // ? } }
javac — Slide18.java (Shape without draw)
Slide18.java:11: error: cannot find symbol someShape.draw(); // ? ^ symbol: method draw() location: variable someShape of type Shape 1 error
❓ Solutions?

Declare draw() in Shape, so that the compiler knows every Shape has it. But Shape cannot give a sensible drawing for an arbitrary shape, so draw() should be an abstract method — and then Shape must be an abstract class. That is version 2 below. (Casting, ((Star) someShape).draw();, also compiles, but only works if you already know the object is a Star — it does not solve the general problem.)

Version 2 Shape is abstract with an abstract draw() Slide 19

📄 Slide 19 — abstract Shape, Star and Crescent ▼
abstract class Shape { public abstract void draw(); } class Star extends Shape { void draw() { ... } ... } class Crescent extends Shape { void draw() { ... } }
❓ Are the following codes correct now?
Shape someShape = new Star();
Shape someShape = new Shape();
someShape.draw();
  • Shape someShape = new Star(); — legal, because a Star is a Shape.
  • Shape someShape = new Shape(); — no longer legal: Shape is abstract and cannot be instantiated.
  • someShape.draw(); — legal, because every actual instance must have a draw() method: the only objects a Shape variable can refer to are of concrete subclasses, and each of them was forced to implement draw().
⚠ One detail the slide skips — access modifier

On the slide, Star writes void draw() (package access) while Shape declares public abstract void draw(). An overriding method cannot be less visible than the method it overrides, so the exact slide code does not compile:

Slide19.java:3: error: draw() in Star cannot override draw() in Shape void draw() { System.out.println("Drawing a star"); } ^ attempting to assign weaker access privileges; was public 1 error

Write public void draw() in the subclasses (as below).

📄 Slide19.java — complete, runnable version ▼
abstract class Shape { public abstract void draw(); } class Star extends Shape { public void draw() { System.out.println("Drawing a star"); } } class Crescent extends Shape { public void draw() { System.out.println("Drawing a crescent"); } } public class Slide19 { public static void main(String[] args) { Shape someShape = new Star(); // legal: a Star is a Shape someShape.draw(); // legal: every actual Shape object has draw() someShape = new Crescent(); someShape.draw(); // Shape other = new Shape(); // no longer legal: Shape is abstract } }
Output — Slide19.java
Drawing a star Drawing a crescent

3 Legal or Illegal? — GeometricObject Statements

Use GeometricObject, Circle and Rectangle from Lesson 3, Section 3. Decide for each statement: legal or illegal?

❓ Legal or illegal? Slide 20
GeometricObject s = new GeometricObject();
GeometricObject s = new Circle(4);
double area = s.getArea();
Circle c = new Circle(3);
c.setColour(GREEN);
area = c.getArea();
StatementVerdictWhy
GeometricObject s = new GeometricObject();✗ illegalGeometricObject is abstract; cannot be instantiated.
GeometricObject s = new Circle(4);✓ legalA Circle is a GeometricObject — an abstract class can be a variable type.
double area = s.getArea();✓ legalgetArea() is declared (abstract) in GeometricObject; at run time Circle.getArea() runs.
Circle c = new Circle(3);✓ legalCircle is concrete.
c.setColour(GREEN);✓ legalA Circle inherits the concrete colour setter of its superclass (see the note below).
area = c.getArea();✓ legalCircle implements getArea().

Only the first statement is illegal (the slide marks it X; the other five √).

javac — the illegal statement
Slide20Bad.java:3: error: GeometricObject is abstract; cannot be instantiated GeometricObject s = new GeometricObject(); ^ 1 error
⚠ Two notes if you type these lines into one program
  • One statement at a time. Lines 1 and 2 both declare s; in one method the second declaration gives "variable s is already defined in method main(String[])". Treat each line as a separate question (or write s = new Circle(4);).
  • setColour(GREEN) follows the slide-13 Shape style (an int colour and constants such as BLACK). Liang's GeometricObject spells it setColor(String), so with the Lesson 3 code you write c.setColor("green"); (with the exact slide text javac reports "cannot find symbol"). Either way the idea is the same: a concrete method inherited from the abstract superclass can be called on a Circle.

4 A Concrete Method Overridden to Be Abstract

📄 Slide 21 — as on the slide ▼
Class Object { public String toString() { ... } } Class Animal { public abstract String toString(); }
❓ What happened? Slide 21

Object.toString() is a concrete method (it has a body). Animal (a subclass of Object) overrides it and declares it abstract — the body is "taken away". A subclass can override a method from its superclass to define it abstract. Because Animal now contains an abstract method, Animal must be defined abstract (abstract class Animal). On the slide Class is pseudo-code; in Java it is class (lower case) and Object already exists in java.lang.

❓ Why? For what reason?

This is rare, but useful when the implementation of the method in the superclass becomes invalid in the subclass. Object's toString() prints something like Cat@1b6d3586, which is useless for animals; making it abstract in Animal forces every concrete animal to write its own meaningful toString(). In this case the subclass (Animal) must be defined abstract.

javac — Animal not declared abstract
Animal.java:1: error: Animal is not abstract and does not override abstract method toString() in Animal class Animal { ^ 1 error
📄 TestAnimals.java — correct Java version ▼
abstract class Animal { @Override public abstract String toString(); // Object.toString() is concrete; here it becomes abstract } class Cat extends Animal { @Override public String toString() { return "Cat: says meow"; } } class Camel extends Animal { @Override public String toString() { return "Camel: lives in the desert"; } } public class TestAnimals { public static void main(String[] args) { Animal[] animals = { new Cat(), new Camel() }; for (Animal a : animals) System.out.println(a); // println calls toString() } }
Output — TestAnimals.java
Cat: says meow Camel: lives in the desert
javac — a subclass that forgets toString() (class Dog extends Animal { })
Dog.java:5: error: Dog is not abstract and does not override abstract method toString() in Animal class Dog extends Animal { } ^ 1 error

5 The Manager Technique — Forcing toString()

This is a real-world application of Rule 8 that every software manager should know.

💼 Real Scenario at a Software Company

👨‍💼 Software Manager:
Every class in our system must have a meaningful toString() method. This is our company standard — no exceptions!
👤 Junior Developer:
But manager, I always forget! When I create many classes, I sometimes miss it. Can you remind me?
👨‍💼 Manager (smiling):
I should not have to remind you every time. Let me make the compiler remind you instead!
💼 The Manager Technique — Making toString() Mandatory ▼
// ── Step 1: Create a base class that forces toString() ────────── abstract class BaseEntity extends Object { // Take toString() from Object (which has a concrete version) // and re-declare it as ABSTRACT — this forces ALL subclasses to implement it! @Override public abstract String toString(); } // ── Step 2: All developers extend BaseEntity ───────────────────── class Student extends BaseEntity { private String name; private int id; public Student(String name, int id) { this.name = name; this.id = id; } // Compiler FORCES the developer to write this — they cannot skip it! @Override public String toString() { return "Student[id=" + id + ", name=" + name + "]"; } } class Course extends BaseEntity { private String code; private int credits; public Course(String code, int credits) { this.code = code; this.credits = credits; } @Override public String toString() { return "Course[" + code + ", credits=" + credits + "]"; } } // ── What happens if someone forgets? ───────────────────────────── class LazyDeveloper extends BaseEntity { private String data; // ❌ COMPILE ERROR: "LazyDeveloper is not abstract and does not // override abstract method toString() in BaseEntity" // The compiler forces them to implement it — manager is happy! }
🎉 Why This Is Powerful
  • The compiler becomes the manager's assistant — no reminders needed
  • A developer cannot compile their class without providing a proper toString()
  • This technique combines Rule 6 (abstract subclass of concrete superclass) and Rule 8 (making a concrete method abstract)
  • Used in real Java frameworks and large enterprise codebases
