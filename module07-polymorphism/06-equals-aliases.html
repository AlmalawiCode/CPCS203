1 Equality: When Are Two Objects “Equal”?

Consider these two assignments:

Two separate Things▼
Thing thing1 = new Thing(); Thing thing2 = new Thing();
🤔 Question (slide 65) — Are these two “Things” (thing1 and thing2) equal?
That’s up to the programmer!
They are two different objects. Whether they count as “equal” depends on what equality means for a Thing — and the programmer decides that by writing an equals method (Sections 4–6). If Thing does not define equals, Java’s default says not equal (false), because they are different objects.

Now consider:

Two references to one Thing▼
Thing thing3 = new Thing(); Thing thing4 = thing3;
🤔 Question (slide 65) — Are these two “Things” (thing3 and thing4) equal?
Yes, because they are the same Thing!
thing4 = thing3 copies the reference, not the object. Both variables point to one object, so any sensible test of equality says true.

We ran it with an empty class Thing { }:

ThingDemo.java▼
class Thing { } public class ThingDemo { public static void main(String[] args) { Thing thing1 = new Thing(); Thing thing2 = new Thing(); System.out.println(thing1 == thing2); System.out.println(thing1.equals(thing2)); Thing thing3 = new Thing(); Thing thing4 = thing3; System.out.println(thing3 == thing4); System.out.println(thing3.equals(thing4)); } }

2 The == Operator: Primitives vs Objects

✅ Primitives (slide 66)

== on int values▼
int x = 9; int y = 9; if (x == y) // true: both hold the value 9
✔ Rule

Primitives can always be tested for equality with ==. A primitive variable holds the value itself, so == compares the two values.

⚠️ Objects (slides 67–69)

⚠️ Rule

For objects, == tests whether the two are the same object. A reference variable holds the address of an object, so == compares addresses, not contents. Two Integers or Strings may or may not be ==!

Case 1 — both created with new (slide 67):

new + new▼
Integer x = new Integer(9); // or String x = new String("abc"); Integer y = new Integer(9); // or String y = new String("abc"); if (x == y) // No (false): two different objects that both contain 9

Case 2 — one with new, one literal (slide 68):

new + literal▼
Integer x = new Integer(9); // or String x = new String("abc"); Integer y = 9; // or String y = "abc"; if (x == y) // No (false): new always makes a brand-new object

Case 3 — both literals (slide 69):

literal + literal▼
Integer x = 9; // or String x = "abc"; Integer y = 9; // or String y = "abc"; if (x == y) // Yes (true): both refer to the SAME shared object

🏊 Why case 3 is true: the String pool (slides 68, 69, 64)

Java keeps one shared copy of every string literal in a special area of the heap called the String pool. When two variables are assigned the same literal, they both get the address of the same pooled object. new String("Cat") ignores the pool and always creates a new object on the heap.

String s1 = "Cat";  → pool "Cat"
String s2 = "Cat";  → pool "Cat"
String s3 = new String("Cat");  → new "Cat"
s1 == s2;  // true
s1 == s3;  // false
Java Heap
String Pool
"Cat"  ← s1, s2
"Dog"
"Cat"  ← s3 (outside the pool)
📝 Integer works the same way — with a limit

Integer y = 9; is autoboxing: Java calls Integer.valueOf(9), which returns a shared cached object for values from −128 to 127. That is why two literal 9s are ==. Outside that range each boxing creates a new object, so Integer a = 1000, b = 1000; gives a == b → false. This is exactly why the slide says “Two Integers or Strings may or may not be ==”.

Modern Java: the constructor new Integer(9) used on the slides is deprecated (the compiler warns “Integer(int) in Integer has been deprecated and marked for removal”). Today we write Integer.valueOf(9) or simply Integer x = 9;. We keep new Integer(9) here only because it is on the slides and shows “two separate objects”.

We compiled and ran all of these cases (Java 21):

EqualityDemo.java▼
public class EqualityDemo { public static void main(String[] args) { int x = 9, y = 9; System.out.println("int: x == y -> " + (x == y)); Integer a = new Integer(9), b = new Integer(9); System.out.println("new Integer(9) == new Integer(9) -> " + (a == b)); System.out.println("a.equals(b) -> " + a.equals(b)); String s = new String("abc"), t = new String("abc"); System.out.println("new String == new String -> " + (s == t)); System.out.println("s.equals(t) -> " + s.equals(t)); Integer c = 9; String u = "abc"; System.out.println("new Integer(9) == 9 (literal) -> " + (a == c)); System.out.println("new String(\"abc\") == \"abc\" -> " + (s == u)); Integer d = 9; String v = "abc"; System.out.println("Integer 9 == Integer 9 (literals) -> " + (c == d)); System.out.println("\"abc\" == \"abc\" -> " + (u == v)); Integer p = Integer.valueOf(9), q = Integer.valueOf(9); System.out.println("Integer.valueOf(9) == Integer.valueOf(9) -> " + (p == q)); Integer big1 = 1000, big2 = 1000; System.out.println("Integer 1000 == Integer 1000 -> " + (big1 == big2)); System.out.println("big1.equals(big2) -> " + big1.equals(big2)); System.out.println("a.intValue() == b.intValue() -> " + (a.intValue() == b.intValue())); String s1 = "Cat", s2 = "Cat", s3 = new String("Cat"); System.out.println("s1 == s2 -> " + (s1 == s2)); System.out.println("s1 == s3 -> " + (s1 == s3)); System.out.println("s1.equals(s3) -> " + s1.equals(s3)); } }

3 Quiz: Predict the == Results

This is the program on slide 70. Predict each of the four values before you look at the answer.

test.java (slide 70)▼
public class test { public static void main(String[] args) { Integer x1 = new Integer(9); String x2 = new String("abc"); Integer y1 = 9; Integer z1 = 9; String y2 = "abc"; String z2 = "abc"; System.out.print(x1 == y1); System.out.print(x2 == y2); System.out.print(y1 == z1); System.out.print(y2 == z2); } }
🤔 Question (slides 70–71) — What are x1 == y1, x2 == y2, y1 == z1 and y2 == z2?
x1 == y1 → false — new Integer(9) is a new object; y1 is the cached 9.
x2 == y2 → false — new String("abc") is outside the pool; y2 is the pooled "abc".
y1 == z1 → true — both autobox 9, and 9 is in the cache (−128..127): same object.
y2 == z2 → true — both are the same literal, so the same object in the String pool.
Because the program uses print (not println), the four values appear on one line: falsefalsetruetrue.

4 The equals Method

Objects can be tested with the method public boolean equals(Object o) of the Object class. Because every class extends Object, every object has it:

Calling equals▼
Obj1.equals(Obj2);
🤔 Question (slide 72) — Obj1.equals(Obj2); What does it do (if the class does not override equals)?
The default implementation of equals in the Object class is: 
public boolean equals(Object obj) {
  return this == obj;
}
This implementation checks whether two reference variables point to the same object, using the == operator. So by default equals means exactly the same as ==.
Default equals in class Object (slide 72)▼
public boolean equals(Object obj) { return this == obj; }
💡 What equals is meant for (slide 73)
  • The equals() method is intended to compare the contents of two objects.
  • You should override this method in your custom class to test whether two distinct objects have the same content.
  • The equals method is overridden in many classes in the Java API, such as java.lang.String and java.util.Date, to compare whether the contents of two objects are equal.

🔍 Strings and arrays (slide 74)

🤔 Question (slide 74) — Obj1 and Obj2 are Strings. What does Obj1.equals(Obj2) do?
equals is overridden in the class String: it compares the characters. new String("abc").equals("abc") is true even though == gives false.
🤔 Question (slide 74) — Obj1 and Obj2 are arrays. What does Obj1.equals(Obj2) do?
equals is not overridden for arrays, so it is the Object version: like ==, it tests if its operands are the same array. Two different arrays with the same elements give false. To compare contents use java.util.Arrays.equals(a1, a2).
ArrayEquals.java▼
import java.util.Arrays; public class ArrayEquals { public static void main(String[] args) { int[] a1 = {1, 2, 3}; int[] a2 = {1, 2, 3}; int[] a3 = a1; System.out.println(a1 == a2); // different arrays System.out.println(a1.equals(a2)); // NOT overridden for arrays System.out.println(Arrays.equals(a1, a2)); // compares the elements System.out.println(a1 == a3); // same array } }
java ArrayEquals
false false true true

5 Morals: How to Test Equality Correctly

⚠️ Morals (slide 75)
  • Never use == to test equality of Strings or arrays or other objects.
  • Use equals for Strings, and java.util.Arrays.equals(a1, a2) for arrays.
  • If you test your own objects for equality, override equals.

For example, the equals method is overridden in the Circle class: two circles are equal when they have the same radius.

Circle overrides equals(Object) — slide 75, inside a runnable program▼
public class MoralDemo { public static void main(String[] args) { Circle c1 = new Circle(5); Circle c2 = new Circle(5); Circle c3 = new Circle(9); Object o = new Circle(5); System.out.println(c1 == c2); // two different objects System.out.println(c1.equals(c2)); // same radius System.out.println(c1.equals(c3)); // different radius System.out.println(c1.equals(o)); // declared Object, actually a Circle System.out.println(c1.equals("hello")); // not a Circle at all } } class Circle { private double radius; public Circle(double radius) { this.radius = radius; } @Override public boolean equals(Object o) { if (o instanceof Circle) { return radius == ((Circle)o).radius; } else return false; } }
java MoralDemo
false true false true false
💡 Everything from Lesson 5 is used here

The parameter type is Object (so it really overrides Object.equals), instanceof checks the actual type, and the cast ((Circle)o) is needed to reach radius — see Lesson 5, Section 5. Without the instanceof test, c1.equals("hello") would throw a ClassCastException. The annotation @Override is optional but recommended: the compiler then checks that you really override.

6 The equals Trap: Overloading vs Overriding

Here is a common mistake. The same test program is run with two different versions of Circle:

Test.java (slide 76)▼
public class Test { public static void main(String[] args) { Object circle1 = new Circle(); Object circle2 = new Circle(); System.out.println(circle1.equals(circle2)); } }
(a) equals(Circle) — Overload
class Circle { double radius; public boolean equals(Circle circle) { return this.radius == circle.radius; } }
(b) equals(Object) — Override
class Circle { double radius; public boolean equals(Object o) { return this.radius == ((Circle)o).radius; } }

And remember the method every class inherits from Object:

Inherited from Object▼
public boolean equals(Object obj) { return this == obj; }
🤔 Question (slides 76–77) — What is the output with Circle (a)? With Circle (b)? Which one overloads and which one overrides?
(a) prints false — equals(Circle circle) has a different parameter type, so it overloads equals; it does not replace Object’s version.
(b) prints true — equals(Object o) has the same signature, so it overrides Object’s equals. Both circles have radius 0.0.
java Test  — run once with each Circle
with Circle (a): false with Circle (b): true

🔎 Why? (slide 78)

The output is false if the Circle class in (a) is used

The Circle class has two overloaded methods: equals(Circle circle) defined in the Circle class and equals(Object o) defined in the Object class, inherited by Circle. At compile time, circle1.equals(circle2) is matched to equals(Object o), because the declared type for circle1 and circle2 is Object (the class Object has only equals(Object)).

In (a), method equals(Object o) is used at both compile time and run time. circle1 and circle2 have different addresses, leading to "false" output. Method overriding follows dynamic binding (determined by the actual type), but method overloading is always determined by the declared type.

The output is true if the Circle class in (b) is used

The Circle class overrides the equals(Object o) method defined in the Object class. At compile time, circle1.equals(circle2) is matched to equals(Object o), and at runtime the equals(Object o) method implemented in the Circle class is invoked (dynamic binding, Lesson 3).

📝 Extra checks we ran
  • With Circle (a) but variables declared as Circle circle1 = new Circle(); Circle circle2 = new Circle(); the output becomes true: now the compiler can see equals(Circle) and picks it. Same objects, different answer — only because the declared type changed. That is why overloading equals is a trap.
  • Circle (b) has no instanceof test, so circle1.equals("hello") throws ClassCastException: class java.lang.String cannot be cast to class Circle. The Morals version in Section 5 (with instanceof) returns false instead.

7 NOTE: == versus equals

Operator / method What it is used for
== Used for comparing two primitive data type values, or for determining whether two objects have the same references.
equals Intended to test whether two objects have the same contents, provided that the method is modified (overridden) in the defining class of the objects.
💡 Stronger test

The == operator is stronger than the equals method, in that the == operator checks whether the two reference variables refer to the same object. If a == b is true, then a.equals(b) is also true (for any sensible equals) — but not the other way round.

8 Aliases

🔗 Definition (slide 80)

Two or more references that refer to the same object are called aliases of each other. One object can be accessed using multiple reference variables (for example c1 and c2).

The picture on slide 80 shows the memory after c1 = c2;, where c1 first referred to a circle with radius 5 and c2 to a circle with radius 9:

After c1 = c2:
c1 ● → C2 circle
c2 ● → C2 circle
c1: Circle
radius = 5
(no reference left → garbage)
C2: Circle
radius = 9
← c1 and c2 (aliases)
⚠️ Manage aliases carefully (slide 81)
  • Aliases can be useful but should be managed carefully.
  • Changing an object through one reference changes it for all of its aliases, because there is really only one object.
  • This doesn’t work for Strings: a String object can never be changed (it is immutable). An operation like s1 = s1 + " there" creates a new String and moves only s1 to it; the alias s2 still sees the old text.
AliasDemo.java▼
public class AliasDemo { public static void main(String[] args) { Circle c1 = new Circle(5); Circle c2 = new Circle(9); c1 = c2; // c1 and c2 are now aliases System.out.println(c1 == c2); System.out.println("c1 radius = " + c1.getRadius()); c2.setRadius(20); // change the object through c2 ... System.out.println("c1 radius = " + c1.getRadius()); // ... c1 sees it too String s1 = "Hi"; String s2 = s1; // s1 and s2 are aliases s1 = s1 + " there"; // creates a NEW String object System.out.println("s1 = " + s1); System.out.println("s2 = " + s2); } } class Circle { private double radius; public Circle(double radius) { this.radius = radius; } public double getRadius() { return radius; } public void setRadius(double r) { radius = r; } }

true

After c1 = c2 there is one Circle with two names, so changing it through c2 is visible through c1. The circle with radius 5 has no reference any more (garbage). For Strings, s1 + " there" builds a new object, so s2 keeps "Hi".

💡 Lesson summary
  • == on primitives compares values; on objects it compares references (same object?).
  • Literal Strings share one pooled object; new always makes a new object — so never rely on == for objects.
  • Object.equals is just this == obj; String, Integer, Date… override it to compare contents. Arrays do not — use Arrays.equals.
  • Override equals(Object o), never write equals(Circle c) (that only overloads). Use instanceof + cast inside.
  • Aliases: several references, one object — a change through one is seen by all (not for immutable Strings).
