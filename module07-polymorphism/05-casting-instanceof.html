1 Legal Assignments: Widening & Narrowing

Before casting objects, remember how casting works with primitive values. You have already used the cast operator (int) to convert one primitive type to another.

✅ Widening is legal
small type → bigger type (e.g. int → double)
Java does it automatically — no information can be lost.
⚠️ Narrowing is illegal (unless you cast)
bigger type → smaller type (e.g. double → int)
Information may be lost, so you must write the cast yourself.
Test.java — legal and illegal assignments (slide 49)▼
class Test { public static void main(String args[]) { double d; int i; d = 5; // ✔ widening: int 5 becomes double 5.0 i = 3.5; // ✘ COMPILE ERROR: narrowing without a cast i = (int) 3.5; // ✔ narrowing WITH a cast: i becomes 3 } }
javac Test.java — the line i = 3.5;
Test.java: error: incompatible types: possible lossy conversion from double to int i = 3.5; ^
💡 Why is i = (int) 3.5; allowed?

Since double is a bigger data type than int, you can explicitly downcast a double to an int in Java. double is a 64-bit primitive value; when you cast it to a 32-bit int, anything after the decimal point is lost: (int) 3.5 is 3, and (int) 9.99 is 9 (the value is cut, not rounded).

🤔 Question — Which of the three assignments on the slide are legal (✔) and which is illegal (✘)?
The three statements▼
d = 5; i = 3.5; i = (int) 3.5;
✔ d = 5; — widening (int → double), automatic. d holds 5.0.
✘ i = 3.5; — narrowing without a cast: compile error "possible lossy conversion from double to int".
✔ i = (int) 3.5; — narrowing with an explicit cast. i holds 3 (the .5 is lost).

2 Casting Objects: Implicit and Explicit Casting

You have already used the casting operator to convert variables of one primitive type to another. Casting can also be used to convert an object of one class type to another within an inheritance hierarchy.

✅ Implicit casting (slide 50)

Every class in Java is a subclass of Object. Look at this method and this call:

Passing a Student where an Object is expected▼
public static void m(Object x) { ... } m(new Student()); // ✔ legal // Passing the argument is the same as the assignment: Object x = new Student();
✔ Implicit casting

The statement Object x = new Student(); is known as implicit casting. It is legal because an instance of Student is automatically an instance of Object. You do not write any cast — Java does it for you.

❌ The other direction (slide 51)

Passing an Object where a Student is expected▼
public static void m(Student x) { ... } m(new Object()); // ✘ COMPILE ERROR // Same as the assignment: Student x = new Object(); // ✘ COMPILE ERROR
javac — both lines are rejected
error: incompatible types: Object cannot be converted to Student m(new Object()); ^ error: incompatible types: Object cannot be converted to Student Student x = new Object(); ^
🤔 Question (slide 51) — Why does Object x = new Student() work, but Student x = new Object() doesn’t?
Because a Student object is always an instance of Object, but an Object is not necessarily an instance of Student.
Every student IS-A object, so the upward assignment is always safe. A plain Object has none of the Student fields and methods, so it can never be used as a Student.

⚠️ When is casting necessary? (slide 52)

Go back to the legal call m(new Student()) with public static void m(Object x), so inside m we have Object x = new Student();. Suppose you want to assign the object reference x to a variable of the Student type:

Assigning x back to a Student variable▼
Object x = new Student(); Student a = x; // ✘ COMPILE ERROR: Object cannot be converted to Student Student a = (Student) x; // ✔ explicit casting
🤔 Question (slide 52) — We can see that x is really a Student. Why does Student a = x; fail, and what do we do?
Even though you can see that x is really a Student object, the compiler is not so clever to know it — it only looks at the declared type Object.
Solution: use an explicit casting: Student a = (Student) x;

3 The Fruit, Apple and Orange Analogy

You may also consider the analogy of fruit, apple, and orange, with the Fruit class as the superclass for Apple and Orange.

The hierarchy▼
class Fruit { } class Apple extends Fruit { } class Orange extends Fruit { }
🤔 Question (slide 53) — For each line, decide: legal, compile error, or runtime exception?
Four statements▼
Fruit fruit = new Apple(); // (1) Apple x = fruit; // (2) Apple x = (Apple) fruit; // (3) Orange x = (Orange) fruit; // (4)
(1) ✔ Legal — an apple is a fruit (upcasting, automatic).
(2) ✘ Compile error — a fruit is not necessarily an apple ("incompatible types: Fruit cannot be converted to Apple").
(3) ✔ Legal — you have to use explicit casting to assign an instance of Fruit to a variable of Apple. The object really is an Apple, so it works at runtime too.
(4) ✘ Exception — it compiles (Orange is a subclass of Fruit), but the object is an Apple, not an Orange, so at runtime Java throws a ClassCastException.

We compiled and ran lines (1), (3) and (4) together:

java FruitDemo
Apple x = (Apple) fruit; worked Exception in thread "main" java.lang.ClassCastException: class Apple cannot be cast to class Orange (Apple and Orange are in unnamed module of loader 'app') at FruitDemo.main(FruitDemo.java:9)

4 Upcasting & Downcasting

Sections 2 and 3 used Object/Student and Fruit/Apple. The same two directions have names — upcasting and downcasting (slides 55–56):

⬆️ Upcasting
It is always possible to cast an instance of a subclass to a variable of a superclass (known as upcasting), because an instance of a subclass is always an instance of its superclass.
Fruit f = new Apple();
⬇️ Downcasting
When casting an instance of a superclass to a variable of its subclass (known as downcasting), explicit casting must be used to confirm your intention to the compiler with the (SubclassName) cast notation.
Apple a = (Apple) f;

🆕 The 5 Assignment Scenarios

When you assign one variable to another, the reference types on both sides determine what the compiler allows. There are exactly 5 situations:

✅ Scenario A Polymorphic ← Polymorphic
Scenario A — Shape ← Shape▼
Shape s1 = new Circle("Red", 5.0); // s1 has reference type Shape Shape s2 = s1; // ✅ Polymorphic ← Polymorphic: Always OK!
Both sides are Shape. Same reference type on both sides. Simple assignment — no casting needed. ✔
✅ Scenario B Polymorphic ← Specific  —  Upcasting (Automatic)
Scenario B — Shape ← Circle (upcasting)▼
Circle c = new Circle("Red", 5.0); Shape s = c; // ✅ Polymorphic ← Specific: Upcasting! Automatic. // Also works inline in one statement: Shape s2 = new Circle("Blue", 3.0); // ✅ Same thing!
A Circle IS-A Shape — assigning to a broader type always works. Java automatically widens the reference. This is called Upcasting (going up the hierarchy). No cast syntax needed. ✔
⚠️ Scenario C Specific ← Polymorphic  —  Needs Explicit Cast!
Scenario C — Circle ← Shape (must downcast)▼
Shape s = new Circle("Red", 5.0); // ❌ COMPILE ERROR — compiler refuses without a cast // Circle c = s; // ✅ Downcasting — you tell the compiler: "trust me, it IS a Circle" Circle c = (Circle) s;
The Shape variable could hold any subclass (Circle, Rectangle, Triangle…). The compiler refuses the assignment without an explicit cast. By writing (Circle), you promise the compiler it is a Circle. This is called Downcasting. ⚠️
✅ Scenario D Specific ← Specific (Same Type)
Scenario D — Circle ← Circle▼
Circle c1 = new Circle("Red", 5.0); Circle c2 = c1; // ✅ Specific ← Specific (same type): Always OK!
Same reference type on both sides. No polymorphism involved — just a normal assignment. ✔
❌ Scenario E Specific ← Specific (Different Type)  —  Compile Error
Scenario E — Circle ← Rectangle (error!)▼
Rectangle r = new Rectangle("Blue", 4.0, 6.0); // ❌ COMPILE ERROR — Circle is NOT a Rectangle! // Circle c = r; // ❌ STILL a compile error — even with a cast! // Circle c = (Circle) r;
Circle and Rectangle are sibling classes — neither is a subclass of the other. This is always an error, and no cast can fix it. The compiler catches it immediately. ✖
Scenario Left Side (target) Right Side (source) Result
A Shape (poly) Shape variable (poly) ✅ Always OK
B Shape (poly) Circle variable or new Circle() ✅ Upcasting (automatic)
C Circle (specific) Shape variable (poly) ⚠️ Needs (Circle) cast — Downcasting
D Circle (specific) Circle variable (same type) ✅ Always OK
E Circle (specific) Rectangle variable (different type) ❌ Compile Error

🤔 Why Can't the Compiler Just See What's Inside?

Students always ask this question: "I can clearly see on the same line that it's a Circle — why does the compiler complain and demand a cast?"

This is one of the most important things to understand in all of Java. Let us explain it step by step.

👀 AT COMPILE TIME
What the compiler sees:
Shape s = ???;

// Could be any subclass:
// new Circle(...)
// new Rectangle(...)
// new Triangle(...)
// new Pentagon(...)
// new Hexagon(...)
// ...
❌ The compiler only sees the reference type.
It cannot look inside — it has no idea what
object will actually be stored there.
▶︎ AT RUNTIME
What Java sees when it executes:
Shape s = new Circle("Red", 5.0);
✅ Now Java KNOWS the actual object is a Circle!
Objects are only born in memory when
new runs — this happens at runtime.
🧠 The Guard at the Door

Imagine the compiler is a guard at a gate. It sees a box labeled "Shape". It cannot open the box — it can only read the label. When you try to give that box to someone who accepts only "Circle" boxes, the guard says: "I cannot guarantee this box contains a Circle! For all I know, it could be a Rectangle!"

By writing (Circle) s, you tell the guard: "I have personally checked — I promise it is a Circle. Let it through." The guard lets it pass. But if you lied — Java will crash at runtime!

💡 The Core Rule
  • The compiler makes all decisions based on the reference type (left of =)
  • The JVM at runtime knows the actual object type (right of =)
  • Objects are only created when new runs — that is always runtime, never compile time
  • A polymorphic reference hides its contents from the compiler — that is exactly the point of polymorphism!

Look at the code first and think about what happens — then reveal the answer:

Shape s = new Circle("Red", 5.0); Circle c = s;
❌ Compile Error!
Even though we can see s holds a Circle, the compiler only sees the reference type Shape. It refuses to assign a Shape variable to a Circle variable without an explicit cast.
Fix: Circle c = (Circle) s;
🤔 Challenge 2 — Will this crash?
👁︎ Show Code ▼
Shape s = new Rectangle("Blue", 4.0, 6.0); Circle c = (Circle) s;
⚠️ Compiles fine — but crashes at runtime!
The cast (Circle) satisfies the compiler. But when Java runs the code, it finds a Rectangle inside — not a Circle. Java throws:
java.lang.ClassCastException: Rectangle cannot be cast to Circle
🤔 Challenge 3 — Upcasting: do you need a cast?
👁︎ Show Code ▼
Triangle t = new Triangle("Green", 6.0, 4.0); Shape s = t;
✅ OK — no cast needed!
This is upcasting: assigning a specific type (Triangle) to a polymorphic type (Shape). Since Triangle IS-A Shape, Java does this automatically. No cast syntax required.

Danger ClassCastException — The Runtime Trap

A ClassCastException is a runtime error — your program compiles successfully but crashes when it runs. It happens when you cast to the wrong type.

🚫 ClassCastException — wrong cast at runtime▼
Shape s = new Rectangle("Blue", 4.0, 6.0); // The compiler is happy — you provided a cast! Circle c = (Circle) s; // ✅ Compiles fine // ❌ But at runtime: ClassCastException! // s actually holds a Rectangle — not a Circle!
🚨 Runtime Error Message:
Exception in thread "main" java.lang.ClassCastException:
    class Rectangle cannot be cast to class Circle

Safe The Solution: Check with instanceof First

Always ask Java: "what type is really inside this variable?" before casting. Use instanceof to check — then cast safely:

✅ Safe downcasting with instanceof▼
Shape s = new Circle("Red", 5.0); // ✅ Always check FIRST — then cast if (s instanceof Circle) { Circle c = (Circle) s; System.out.println("Diameter: " + c.getDiameter()); } else if (s instanceof Rectangle) { Rectangle r = (Rectangle) s; System.out.println("Width: " + r.getWidth()); } else { System.out.println("Unknown shape type"); }
📚 Coming Next: Generics — No More Casting Errors!

The danger of ClassCastException is real. But there is a solution: Lesson 7 (ArrayList) gives a first look, and a later chapter teaches Generics in full (e.g., ArrayList<Circle> instead of ArrayList<Shape>).

Generics let you tell the compiler exactly what type to expect — so mistakes are caught at compile time instead of crashing at runtime. Generics solve the root problem that makes casting dangerous.

📝 Important Clarification: IS-A and Interfaces

We said the condition for polymorphism is the IS-A relationship through inheritance. This is the main rule for this chapter. A Student is not a Shape. A Car is not a Shape. A Book is not a Shape. That is why polymorphism only works within an inheritance hierarchy.

However, you may wonder: what about a Car and a Book? They have nothing in common through inheritance — but both could implement the same interface (for example, Sellable). Interfaces also create an IS-A relationship!

🔒 Rule for this chapter: IS-A means inheritance only. Interfaces are a future topic. The key idea is: polymorphism requires a common type connecting the objects. Whether that connection comes from inheritance or an interface, the concept is the same — but the IS-A from interfaces is a topic for the next chapter.
💡 Casting Summary
  • Poly ← Poly: Always OK (same reference type)
  • Poly ← Specific: Upcasting — Automatic ✔ (IS-A guarantees it)
  • Specific ← Poly: Downcasting — needs explicit (Type) cast ⚠️
  • Specific ← Specific (same): Always OK ✔
  • Specific ← Specific (different): Compile Error ✖
  • Always use instanceof before downcasting to prevent ClassCastException

5 Casting from Superclass to Subclass & the instanceof Operator

⚠️ Casting from superclass to subclass may fail (slides 57–58)
  • Explicit casting must be used when casting an object from a superclass to a subclass. This type of casting may not always succeed.
  • For the casting to be successful, you must make sure that the object to be cast is an instance of the subclass.
  • If the superclass object is not an instance of the subclass, a runtime ClassCastException occurs. For example, if an object is not an instance of Student, it cannot be cast into a variable of Student.
  • It is a good practice, therefore, to ensure that the object is an instance of another object before attempting a casting. This can be accomplished using the instanceof operator.

🔍 The instanceof operator (slide 59)

Use the instanceof operator to test whether an object is an instance of a class. The result is true or false.

instanceof before casting (slide 59)▼
Object myObject = new Circle(); ... // Some lines of code /** Perform casting if myObject is an instance of Circle */ if (myObject instanceof Circle) { System.out.println("The circle diameter is " + ((Circle)myObject).getDiameter()); ... }
💡 Why is the cast needed here?

The variable myObject is declared as Object. The declared type decides which method to match at compile time. Using myObject.getDiameter() would cause a compile error, because the Object class does not have the getDiameter method — the compiler cannot find a match for myObject.getDiameter(). Therefore, it is necessary to cast myObject into the Circle type to tell the compiler that myObject is also an instance of Circle.

javac — calling myObject.getDiameter() without a cast
error: cannot find symbol symbol: method getDiameter() location: variable myObject of type Object
📝 Note on the parentheses

Write ((Circle)myObject).getDiameter() with the extra pair of parentheses. The dot operator runs before the cast, so (Circle)myObject.getDiameter() would try to call getDiameter() on an Object first — the same compile error.

6 instanceof in the Staff Payroll Example

Go back to the Staff class from Lesson 4: its array StaffMember[] staffList holds Executive, Employee, Hourly and Volunteer objects. The slide adds two methods that reach the subclass-only methods addHours (only in Hourly) and awardBonus (only in Executive):

Slide 60 — casting a fixed array slot▼
public class Staff { ... public void addHours(int hour) { ((Hourly)staffList[3]).addHours(hour); } //--------------------------------------------------------- public void addBonus(double bonus) { ((Executive)staffList[0]).awardBonus(bonus); } ... }

(On the slide the method and variable are spelled addBouns/bouns; the parameter is bonus, so bouns would not compile. We use addBonus/bonus.)

🤔 Question (slide 60) — We don’t know that staffList[3] is an Hourly object, or that staffList[0] is an Executive object… So, what do we do?
Use the instanceof operator: loop over the whole array and cast only the elements that really are Hourly (or Executive) — see the code below.
In the Lesson 4 array, staffList[3] is actually Maha, a Volunteer, so the slide-60 version crashes with a ClassCastException (we ran it — output below).
Slide 61 — safe versions with instanceof▼
public void addHours(int hour) { /** Perform casting if s is an instance of Hourly */ for (StaffMember s : staffList) if (s instanceof Hourly) ((Hourly)s).addHours(hour); } //--------------------------------------------------------- public void addBonus(double bonus) { for (int i = 0; i < staffList.length; ++i) if (staffList[i] instanceof Executive) ((Executive)staffList[i]).awardBonus(bonus); }

We tested both versions with the five staff members from Lesson 4 (staff.addHours(40); staff.addBonus(500.0); then pay everyone, then call the slide-60 version):

java Staff
Dr. Khalid is paid 5500.0 Faisal is paid 3000.0 Layla is paid 2000.0 Maha is paid 0.0 Ziad is paid 1800.0 --- now the unsafe version --- Exception in thread "main" java.lang.ClassCastException: class Volunteer cannot be cast to class Hourly (Volunteer and Hourly are in unnamed module of loader 'app')

7 Example: Demonstrating Polymorphism and Casting (CastingDemo)

The program creates two objects, a circle and a rectangle, then invokes the displayObject method to display them. displayObject displays the diameter if the object is a circle and the area if the object is a rectangle.

CastingDemo.java (slide 63) — with small Circle and Rectangle classes so it runs▼
public class CastingDemo { public static void main(String[] args) { // Create and initialize two objects Object object1 = new Circle(1); Object object2 = new Rectangle(1, 1); // Display circle and rectangle displayObject(object1); displayObject(object2); } /** A method for displaying an object */ public static void displayObject(Object object) { if (object instanceof Circle) { System.out.println("The circle diameter is " + ((Circle)object).getDiameter()); } else if (object instanceof Rectangle) { System.out.println("The rectangle area is " + ((Rectangle)object).getArea()); } } } class Circle { private double radius; public Circle(double radius) { this.radius = radius; } public double getDiameter() { return 2 * radius; } } class Rectangle { private double width, height; public Rectangle(double width, double height) { this.width = width; this.height = height; } public double getArea() { return width * height; } }
🤔 Question (slide 62 “Run”) — What does CastingDemo print? Why are the casts needed?
The circle diameter is 2.0
The rectangle area is 1.0
The parameter object is declared as Object, which has no getDiameter() or getArea(). instanceof checks the actual object first, then the cast (Circle) / (Rectangle) lets the compiler accept the call. Because of the instanceof test, the casts can never throw a ClassCastException.
java CastingDemo
The circle diameter is 2.0 The rectangle area is 1.0
💡 Polymorphism + casting together

displayObject(Object object) accepts any object (polymorphism: an object of a subclass can be used wherever its superclass type is expected). Inside, instanceof + casting lets us use the subclass-specific methods safely.
