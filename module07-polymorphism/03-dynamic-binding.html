1 Dynamic Binding — Which toString() Is Invoked?

📚 Definition (slides 19–21)

A method can be implemented in several classes along the inheritance chain. Which implementation is used will be determined dynamically by the Java Virtual Machine at runtime.

This capability is known as dynamic binding.

🎓 Slide Example: Person → Student → GraduateStudent

The method m(Object x) accepts any object and calls x.toString(). Four different objects are passed to it.

📄 PolymorphismDemo.java (slide 19)▼
public class PolymorphismDemo { public static void main(String[] args) { m(new GraduateStudent()); m(new Student()); m(new Person()); m(new Object()); } public static void m(Object x) { System.out.println(x.toString()); } } class GraduateStudent extends Student { } // no toString() here! class Student extends Person { public String toString() { return "Student"; } } class Person { // extends Object automatically public String toString() { return "Person"; } }
🤔Question (slide 19) — Which toString() method will be invoked for each call?

Inside m, the parameter x is always declared as Object. Predict the four output lines before you reveal the answer.

Output (slide 20):
java PolymorphismDemo
Student Student Person java.lang.Object@7852e922
  • m(new GraduateStudent()) → GraduateStudent has no toString(), the JVM goes up to Student → "Student"
  • m(new Student()) → Student's own toString() → "Student"
  • m(new Person()) → Person's own toString() → "Person"
  • m(new Object()) → Object's toString(): class name + @ + a hash code in hexadecimal

The declared type of x is always Object, yet the result depends on the actual object — that is dynamic binding. Note: the number after @ changes from run to run (the slide shows @130c19b), and Java prints it with a lowercase java.lang.Object.

🔗 The Inheritance Chain Behind the Example (slide 21)

Object ← Person ← Student ← GraduateStudent. toString() is implemented in three classes of this chain (Object, Person, Student). For every call, the JVM decides at runtime which of these implementations is invoked.

🔷 Object.toString() Overridden in GeometricObject (slide 22)

A method can be defined in a superclass and overridden in its subclass. For example, the toString() method is defined in the Object class and overridden in GeometricObject (the textbook's shape superclass). Consider the following code:

📄 Object o = new GeometricObject();▼
class GeometricObject { // extends Object private String color = "white"; private boolean filled; @Override public String toString() { // overrides Object.toString() return "color: " + color + " and filled: " + filled; } } Object o = new GeometricObject(); System.out.println(o.toString());
🤔Question (slide 22) — Which toString() method is invoked by o?
GeometricObject's toString().
The declared type of o is Object — the compiler accepts the call because Object has a toString(). At runtime the JVM sees that o refers to a GeometricObject, which overrides toString(), so that version runs:
Output
color: white and filled: false

2 Dynamic Binding — The Engine Behind Polymorphism

🔗 Dynamic Binding & Polymorphism Are Partners
Polymorphism is the ability to treat different objects through a common type. Dynamic Binding is the mechanism that makes it work. Without dynamic binding, polymorphism would be useless — the compiler would always call the superclass version and you would never see the subclass behavior. They are inseparable.

⚖ Static Binding vs Dynamic Binding

Java has two strategies for deciding which method to call. Understanding the difference is the entire story of dynamic binding:

⏰ Static Binding
Early Binding — Compile Time
  • Decision made by the compiler
  • Based on the method signature (arguments)
  • Used for overloaded methods
  • Decided before the program runs
▶︎ Dynamic Binding
Late Binding — Runtime
  • Decision made by the JVM
  • Based on the actual object type
  • Used for overridden methods
  • Decided while the program runs

⏰ Static Binding: The Compiler Decides (Overloading)

Imagine a post office with three counters. The sign says:

Counter 1 — for letters  |  Counter 2 — for parcels  |  Counter 3 — for documents

The guard at the entrance looks at what you are holding and immediately directs you to the right counter — right there, at the entrance, before you even walk in. He does not need to wait. He sees a letter → Counter 1. He sees a parcel → Counter 2. The decision is made at the entrance (compile time) based on what you carry (argument type).

Java's compiler is exactly this guard. When it sees overloaded methods and a call with specific arguments, it resolves the correct method immediately — at compile time.

⏰ Static Binding — overloading, compiler decides▼
class Printer { void print(int x) { System.out.println("Integer: " + x); } void print(double x) { System.out.println("Double: " + x); } void print(String x) { System.out.println("Text: " + x); } } Printer p = new Printer(); p.print(42); // ← Compiler sees int → calls print(int) — decided NOW p.print(3.14); // ← Compiler sees double → calls print(double) — decided NOW p.print("hello"); // ← Compiler sees String → calls print(String) — decided NOW // The compiler reads the argument types and immediately knows // which overloaded version to call. No waiting. No surprises. // This is STATIC BINDING.
⏰ Why is it "static"? Because the binding (connection between the call and the method) is established statically — fixed at compile time, before anything runs. The same answer every time, no matter what.

▶︎ Dynamic Binding: The JVM Decides (Overriding)

Now imagine a different scenario. The guard sees a box labeled "Shape". He looks at the label — but cannot see what is inside.

He cannot send it to "Circle Counter" or "Rectangle Counter" yet — because the label only says "Shape." He stamps it getArea() and sends it to the runtime room.

At runtime, the box is opened. Inside: a Circle. The runtime worker sees it — "Ah! It is a Circle! I know exactly what to do." He runs Circle.getArea(). The decision was made at runtime — this is dynamic binding.

▶︎ Dynamic Binding — overriding, JVM decides at runtime▼
Shape s; // reference type = Shape s = new Circle("Red", 5.0); s.getArea(); // Compiler: "Shape has getArea() — OK." (no decision on WHICH one) // JVM at runtime: actual object is Circle → calls Circle.getArea() → 78.54 s = new Rectangle("Blue", 4.0, 6.0); s.getArea(); // Compiler: same check. JVM: actual = Rectangle → 24.00 s = new Triangle("Green", 3.0, 4.0); s.getArea(); // Compiler: same check. JVM: actual = Triangle → 6.00 // Same variable 's'. Same call s.getArea(). THREE different results. // The JVM decides WHICH version at runtime. This is DYNAMIC BINDING.
▶︎ Why is it "dynamic"? Because the binding changes dynamically — it is decided fresh at runtime based on what object actually exists in memory. Different object → different result. Same code, different behavior. That is polymorphism.

👥 The Division of Work: Compiler vs JVM

⏰ COMPILER'S JOB
  • Check that the reference type has the method
  • Shape has getArea()? ✅ Allowed.
  • Does NOT decide which version
  • Stamps the call and passes it along
▶︎ JVM'S JOB (at runtime)
  • Look at the actual object in memory
  • Start at the actual class, search UP the hierarchy
  • Find the most specific overridden version
  • Execute that version

🔎 How the JVM Finds the Right Method

When Java sees s.sound() at runtime, it follows this exact lookup path:

Example: Animal a = new Camel();   a.sound();
Step 1: JVM sees actual object is Camel
↓
Step 2: Does Camel override sound()?  → NO — go UP
↓
Step 3: Does Mammal override sound()?  → YES! — use this one
↓
Execute: Mammal.sound()  →  "Warm-blooded mammal sound"
💡 The Golden Rule of Dynamic Binding

Java starts at the actual object's class and searches upward through the hierarchy until it finds the most recent override of that method. If no subclass overrides it, Java eventually reaches and uses the superclass version.

🏭 Practice: The 4-Level Hierarchy

Study this hierarchy carefully. Some classes override sound(), some do not:

📄 The Animal → Mammal → Camel → Hashi hierarchy▼
class Animal { public void sound() { System.out.println("Generic animal sound"); } } class Mammal extends Animal { @Override public void sound() { System.out.println("Warm-blooded mammal sound"); } } class Camel extends Mammal { // ⚠ Camel does NOT override sound() — it INHERITS Mammal's version! } class Hashi extends Camel { // Hashi = baby camel (حوار) @Override public void sound() { System.out.println("Hwar!"); } }

🤔Exercise 5 — The full chain — trace each call!
👁︎ Show Code ▼

Output:
Generic animal sound  ← Animal (defines, not overridden)
Warm-blooded mammal sound  ← Mammal (overrides Animal)
Warm-blooded mammal sound  ← Camel (no override → goes up to Mammal)
Hwar!  ← Hashi (baby camel, overrides → its own version)
Dynamic binding in full action! Same loop, same call a.sound(), but four different results — each determined at runtime by the actual object type.
💡 Dynamic Binding Summary
  • Static binding: method overloading → compiler decides at compile time based on argument types
  • Dynamic binding: method overriding → JVM decides at runtime based on actual object type
  • The reference type controls what methods you can call
  • The actual object type controls which version runs
  • JVM searches upward from the actual class until it finds an override
  • Dynamic binding is the engine that makes polymorphism work

🔎 The Search Rule (slide 31)

Suppose an object o is an instance of C1 (where C1 → C2 → … → Cn) and o invokes m(). The JVM searches the implementation for the method m in C1, C2, …, Cn-1 and Cn, in this order, until it is found. Once an implementation is found, the search stops, and the first-found implementation is invoked.

If the object is a C2, the search simply starts at C2 — classes below the object's class (like C1) are never searched.

4 Method Matching vs. Binding

⚖ Two Different Issues (slides 32–33)

Matching a method signature and binding a method implementation are two issues.

  • Matching — compile time. The declared type of the reference variable decides which method to match. The compiler finds a matching method according to parameter type, number of parameters, and order of the parameters.
  • Binding — runtime. A method may be implemented in several subclasses. The Java Virtual Machine dynamically binds the implementation of the method at runtime.

🐱 Slide Example: Animal animal = new Cat();

⏰ Compile time — MATCHING
Animal animal = new Cat();
animal.sound();
The compiler looks only at the declared type Animal: does Animal have a sound() with no parameters? → Yes, matched: Animal.sound().
➜
▶︎ Run time — BINDING
actual object: Cat
The JVM looks at the actual object, a Cat. Cat overrides sound() → bound to Cat.sound().

🔢 Matching Uses Type, Number and Order: methodA(int a, char b)

When several overloaded versions exist, the compiler picks the one whose parameter list matches the arguments in type, number and order:

📄 MatchDemo.java — matching (compile time) and binding (runtime)▼
class Animal { public void sound() { System.out.println("Some animal sound"); } } class Cat extends Animal { @Override public void sound() { System.out.println("Meow"); } } public class MatchDemo { static void methodA(int a, char b) { System.out.println("methodA(int, char)"); } static void methodA(char a, int b) { System.out.println("methodA(char, int)"); } static void methodA(int a) { System.out.println("methodA(int)"); } public static void main(String[] args) { Animal animal = new Cat(); animal.sound(); // matched: Animal.sound() bound: Cat.sound() methodA(5, 'x'); // type + number + order -> methodA(int, char) methodA('x', 5); // order reversed -> methodA(char, int) methodA(5); // one parameter -> methodA(int) } }
java MatchDemo
Meow methodA(int, char) methodA(char, int) methodA(int)
💡 Connect it to the C1 … Cn scenarios

Scenario 8 (slide 30) failed at the matching step: the declared type Cn has no m(), so nothing could be matched. All other scenarios passed matching, and then the binding step (the upward search) chose the implementation.

5 Quiz — What Is Wrong in the Following Code?

📄 Test.java (slide 34)▼
1 public class Test { 2 public static void main(String[] args) { 3 Integer[] list1 = {12, 24, 55, 1}; 4 Double[] list2 = {12.4, 24.0, 55.2, 1.0}; 5 int[] list3 = {1, 2, 3}; 6 printArray(list1); 7 printArray(list2); 8 printArray(list3); 9 } 10 11 public static void printArray(Object[] list) { 12 for (Object o: list) 13 System.out.print(o + " "); 14 System.out.println(); 15 } 16 }
🤔Question (slides 34–35) — What is wrong in this code?

Hint: three arrays are passed to a method whose parameter type is Object[]. Which of the three calls is a problem?

Line 8: int[] cannot be passed to Object[]. The program does not compile:
javac Test.java
Test.java:8: error: incompatible types: int[] cannot be converted to Object[] printArray(list3); ^
  • Lines 6 and 7 are fine: Integer and Double are classes (subclasses of Object), so an Integer[] or a Double[] is an Object[].
  • Line 8 is wrong: int is a primitive type, not an object. An int[] is not an array of objects, so it is not an Object[]. (Auto-boxing converts a single int to an Integer, but it never converts a whole int[] into an Integer[].)
  • Fix: declare Integer[] list3 = {1, 2, 3}; — then the program prints:
java Test (after the fix)
